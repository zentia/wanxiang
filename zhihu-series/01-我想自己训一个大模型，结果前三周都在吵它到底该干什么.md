# 我想自己训一个大模型,结果前三周都在吵「它到底该干什么」

> 备选标题:
> - 从零做大模型的第一个坑,不在代码里,在定位里
> - 我给大模型写了三千字「职责说明书」,然后全删了
> - 一个自研大模型项目的三次定位漂移,和它教会我的事

先说结论,免得你读到最后才看到:**一个自研大模型项目最容易翻车的地方,不是算力、不是架构、不是数据,而是「这东西到底该干什么」没定清楚。我在这件事上反复摇摆了三周,把模型一会儿当业务助手、一会儿当问答工具、一会儿当检索系统,最后全砍掉,才回到最朴素的一句话——训一个单纯的、通用的语言模型。** 这篇是这个系列的开头,讲的不是技术,是那些被我浪费掉的时间,以及它们换来的判断。

## 一、最初我想要的其实是「一套会自己进化的系统」

起点是一个挺贪心的念头。我想要的不是某个具体任务的模型,而是三条支柱:

- **模型自己训练**:训练管线能自己跑、自己续、自己判断收没收敛,不用人盯着调;
- **推理自己优化**:导出、部署、生成这一侧能被测量、能被替换,不是一次性脚本;
- **Agent 自己适配**:上层应用能自己接上模型,而不是每个场景都重写一遍胶水代码。

给这套框架起了个代号叫「万象」(化名)。注意,这三条里**没有一条**是「模型要能回答某个业务问题」——我一开始想造的是**基础设施**,不是**应用**。可惜这个初心,后面被我自己弄丢了整整三周。

那时候我顺手做了一些现在看来很典型的设计工作:把职责拆成清单、讨论端侧还是服务端、画部署拓扑、定义客户端怎么调。这些事单看都合理,合在一起却把我一步步带偏了。

## 二、第一次漂移:把它塞进一个具体的业务里

我手上正好有一款自走棋手游(下面叫它 G 项目)。项目里已经有两类 AI:

| 已有的 AI | 干什么 | 归谁 |
|---|---|---|
| 游戏内助手 AI | 玩家侧的实时提示、陪玩式引导 | 玩家体验 |
| 强化学习 bot | 模拟玩家操作、做对局测试和难度校准 | 玩法 / 数值 |

于是我很自然地开始问:那「万象」该站哪个位置?是不是该补上第三类?我甚至认真列过一张面向开发者的日常助手职责表:

- 需求快过期了主动提醒;
- 版本管理系统里提交冲突了,告诉人怎么解;
- 更新完趁机器空闲自动把引擎拉起来刷新;
- 配置表提交前预判会不会出问题;
- 美术资源是不是符合制作规范……

这张表写得越细,我越觉得不对劲。**因为上面每一条,本质上都是「工作流编排 + 检索 + 规则」,几乎不依赖一个「从零训练出来的语言模型」。** 换句话说,我是在给一个还不存在的能力,硬找一批用不上这个能力的场景。这是一个很隐蔽的陷阱:当你的目标是「做一个大模型」时,你会下意识地去找「哪里能用上 AI」,而不是问「哪件事非得靠一个自己训的模型不可」。

部署讨论也在同一个坑里打转。端侧跑?模型塞不进手机,而且要跟着版本发,直接否掉,改成部署在服务器、客户端走 HTTP 调用。实时提示该不该归它?不,那是游戏内助手的职责,别抢。然后是一堆很具体但和「模型质量」毫无关系的工程:一台安卓备用机上装个轻量客户端填地址调服务、局域网能不能连、异地怎么用一个组网工具打通、流式返回里 `finish_reason` 怎么对齐才不报错……这些最后都解决了,但**没有一件让模型变强哪怕一点点**。

> 这一段的教训我后来写成一句话贴在仓库 README 里:目标是一个**通用语言模型框架**,不是一个**业务助手产品**。业务场景是模型炼成之后的应用层,不是立项阶段的动机。

## 三、第二次漂移:为了「能验收」,把任务选成了查字典

定位砍干净之后,我遇到一个非常现实的追问:**那我怎么知道模型「变好了」?** 通用语言能力太虚,得找一个能打分的具体任务。

我当时选了「成语释义」——给它一个成语,让它输出解释。这个选择看起来很聪明:有标准答案、能算字符级准确率、能切训练/留出集。于是有了预训练(M2)、有监督微调(SFT)、一整套冻结的问答评测仪器。

结果这个「聪明的选择」后来让我连着翻了两次车(第 3、4 篇详述),根因一句话:**成语释义是查字典,不是语言建模**。像「白兔赤乌 → 多借指时间」这种映射,不可能从字面推出来,只能背。我等于用一个「记忆力考试」去衡量一个「语言模型」,还煞有介事地为它造了三把不同的尺子。

后来我甚至给它加了一层检索外挂:精确命中词典就直接返回,模型答不出也不硬编。这一步把准确率直接拉到满分(150/150),当时看着很爽——但那分明是**换了个工具**,跟模型强不强没关系。这一步做完,我反而彻底清醒了。

## 四、真正的转折点:一句话把目标砍回原形

在检索方案上线之后,我给自己下了一个很硬的决定,原话大概是:

> **模型的核心目标变了,就是做一个单纯的大模型,跟 G 项目无关,也不是检索。**

这句话把之前所有铺垫一次性清零:业务助手的职责表、成语语料、检索外挂、面向玩家的实时提示……全部从主线上撤下来,**保留为可复现的历史归档,默认不启用**。新增的主线只剩两件事:

1. 一套**通用语料管线**(下载公开中文维基快照 → 确定性切分 → 构建 token 流);
2. 一套**通用语言建模评测**(在冻结留出集上算 token 级交叉熵 / 困惑度)。

而真正让我松一口气的是:**训练核心一行没改**。配置、基座模型、数据加载、checkpoint、训练循环、导出、推理——它们从头到尾只消费一段 uint16 的 token 流,压根不关心这串 token 是成语还是维基百科。当初把它设计成「业务无关」,反而是这三周里唯一没白做的决定。

## 五、回头看,这三周真正买到的东西

| 我一度以为在推进的事 | 实际性质 | 最终处置 |
|---|---|---|
| 写开发者助手职责清单 | 工作流 / 规则产品 | 删,不进模型项目 |
| 端侧 vs 服务端、组网、客户端联调 | 部署工程,与模型质量正交 | 保留为独立文档,与主线解耦 |
| 成语释义 + 三套评测尺子 | 记忆型任务,性质错配 | 归档,不再作为质量判据 |
| 检索外挂满分 | 换工具,非模型能力 | 归档,显式开关才启用 |
| 通用训练核心(只吃 token 流) | 真正的资产 | 成为最终主线 |

如果要给同样想从零训模型的人一句建议,就是:**先把「什么算成功」定义成一个不受你主观愿望影响的量,再去写第一行模型代码。** 我这三周之所以反复,本质上是每次都想用一个「看起来能交差」的东西代替这个定义,结果每次都被更诚实的测量打回来。

有意思的是,当我真的开始认真定义「什么算成功」时,我做的第一件事甚至不是写模型,而是花大力气造了一把**不会骗自己的尺子**——这件事听起来很反直觉,但它是整个项目里回报率最高的投入。
