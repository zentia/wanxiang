# 加长训练、换分词、扩到 1 亿参数:三条路全撞在同一堵墙上

> 备选标题:
> - 三个 `NO_CHANGE` 之后我才明白:问题不在超参,在任务选错了
> - 检索把准确率拉到 150/150 满分,为什么我反而确定「此路不通」
> - 一个 `exact_match` 恒为 0 的实验,教会我区分「换工具」和「模型变强」

结论先行:**当三条完全不同的技术路线——加长训练、换 tokenizer、把参数量放大近 10 倍——得到几乎相同、且都低于阈值的分数时,该怀疑的不是超参,而是「你在让模型做的事」本身。** 这三路全 `NO_CHANGE` 逼我承认一个更根本的错误:我拿一个「查字典」的记忆型任务,去衡量一个「语言模型」的能力。而最后那步「检索满分」的实验,看似是解法,恰恰是把这个错误钉死的证据。

## 一、三条路,一个结果

第 3 篇的污染清干净之后,我有了可信的零样本基线:词级留白(300 个成语的释义从预训练和微调流里整批剔除),150 道计分题,`char_f1 / rouge_l / edit_sim / EM` 加权成 composite,没有 judge、没有语义打分,刻意保守。

在这个干净尺子上,我把当时能想到的三条提升路线全跑了一遍(这里的「扩到 1 亿参数」是历史成语任务阶段那条 14 层 / 768 维 / 12 头、约 105.5M 参数的配置;和后面通用 LM 主线里 29.17M 的扩容是两码事,别混):

| 路线 | 具体改动 | eval3 composite | 结论 |
|---|---|---:|---|
| char 干净基线 | 10M 模型,step1350 | 0.0676 | 可信零点 |
| BPE 子词 tokenizer | 字符 → 保留字符的 BPE | 0.0669 | `NO_CHANGE`(噪声级) |
| 扩容到 100M | 10M → 100M 参数 | 0.0835 | `NO_CHANGE`(真实但不足) |

`QUALITY_THRESHOLD = 0.50`,三条路连零头都够不到。参数翻了近 10 倍,composite 只动了 0.016。**这不像「还没调好」,像「方向不对」。**

## 二、根因:成语释义是「无信息生成」

诊断落在任务性质上。看两个真实例子:

- `白兔赤乌 → 多借指时间`
- `白首相庄 → 指夫妇到老犹相敬爱`

成语释义是**约定俗成的映射,无法从字面推导**。而这 150 个词的释义又被我特意从训练流里全部剔除了——于是模型面对的是一道「既没见过答案、又不可能推理出来」的题。它唯一能做的,是套用训练里最高频的答案外壳。量化证据很干净:

- 训练答案里 **38.7%** 以「比喻 / 形容」开头(6072 + 5785,共 30594 条);
- 参考答案的高频字被「指 / 的 / 比 / 容 / 喻 / 形」占满;
- 所以模型稳定输出「形容…相互转化相互转化…」——**外壳对了,语义全错**,`exact_match` 恒为 0。

这就解释了为什么三条路都撞墙:**这不是容量问题、不是分词粒度问题,是「让模型猜一个它无从得知的事实」。** 把它从 10M 堆到 100M,`exact_match` 依然是 0,因为再大的模型也推不出「白兔赤乌借指时间」。

我当时还顺手排除了一个次要因素:生成预算 `GEN_TOKENS=48`,而训练答案均值只有 10.5 字(p50=10、p90=18),贪心解码又没有重复惩罚,后半段必然进入循环(「相互转化相互转化…」)。**这是放大器,不是根因**——就算把解码修得干净,模型仍然不知道 holdout 成语的意思。把「放大器」当成「根因」去优化,是这类调试里最常见的浪费。

## 三、检索满分,为什么反而是「判死刑」

既然是查字典,那正确工具当然是**查字典**。我加了一层确定性检索(M4):从固定词典构建密封索引,服务层把输入里的《成语》抽出来,精确命中就直接返回词典答案,未命中才回退生成。设计上几个细节我挺满意:

- 索引答案与 SFT 标签、评测参考答案**共用同一个清洗函数**,命中即字节相等;
- 索引带 `manifest.json` 封印,源 sha256 / 条数 / 文件校验和,篡改或截断加载即失败;
- **保守回答**:只有精确命中才用检索作答,模糊召回仅供诊断,绝不返回「看起来像但可能错」的释义;
- **故意不排 holdout**:索引就是要包含全部 30,894 条(含留出词),并在报告里明示,避免把满分误读成泛化。

结果:`exact_match = 1.0`,150/150 满分。

**但我在报告里给它的判词是「换工具,不是模型变强」,并且明确它与 eval3 `INCOMPARABLE`。** 这一步做完,我反而彻底清醒了:如果一个「不依赖模型能力」的词典查询就能把任务做到满分,那这个任务从来就不该用来衡量模型能力。检索层能作为产品功能留着(显式开关才启用),但它把主线证伪了:

> 我用三套尺子、三组实验,反复测量的其实是一个**查表能力**;模型在这条路上无论怎么优化,都不会变成「更好的语言模型」。

## 四、于是做了那个迟早要做的决定

三路 `NO_CHANGE` + 检索满分,凑齐了一个完整的证伪链条:

| 证据 | 排除掉的解释 |
|---|---|
| 加长训练无效 | 不是训练不够 |
| BPE 无效 | 不是分词粒度 |
| 100M 无效 | 不是容量 |
| 检索满分但换工具 | 不是模型能力,是任务性质 |
| `EM` 恒 0、答案外壳高频 | 模型在背套话,不是理解 |

根因不是超参、不是架构、不是数据规模,是**任务性质错配**:把「记住 150 个成语的释义」当成了「语言能力」。既然我真正想要的是一个通用的、单纯的大模型,那就该用真正的语言建模任务——**预测下一个 token**——来训练和测量,而不是记忆型问答。

于是我把 `m2 / sft / eval2 / eval3 / eval4 / retrieval` 全部**归档**(可复现、默认不启用),新增一条独立主线。而且有个让我挺欣慰的发现:

> 训练核心(配置 / 基座 / 数据加载 / checkpoint / 导出 / 推理)**一行代码都不用改**——它们从头到尾只消费一段 uint16 token 流,根本不关心这串 token 是成语词典还是百科正文。

换句话说,前面几十篇文档里的弯路,没有污染到地基。地基是对的,只是我一直在上面盖错的房子。
